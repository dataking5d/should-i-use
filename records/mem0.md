# mem0

**核心用途** — 用 LLM 从对话中自动抽取事实，存入向量库（+可选图），检索后注入上下文，充当 agent 的自动长期记忆层。

**与现有系统的关系** — 与我的 ACP 在**目的**上重叠（为 agent 提供持久上下文），机制相反。ACP 是确定性、人工显式写入的 markdown 热/冷上下文；mem0 是概率性、LLM 自动抽取的向量存储。真实新增只有"自动抽取 + 语义召回"，而这两点恰好是 ACP 主动放弃的特性（为换取可读、可 diff、可控）。与 paper-assistant 的 LanceDB 语义检索在**机制层**部分重叠（向量召回），但那条线是文献知识库，不是对话记忆，不同数据不同触发。

**Whole-project decision** — 没必要引入。它解决的是"多用户 / 记忆量超出可读范围 / 需要按需语义召回"的问题，我没有这个问题；我的记忆是单人、按项目、几 KB 的 markdown。

**Valuable components** —
- 多信号融合检索（semantic + BM25 + entity 并行）——我的 LanceDB 线是纯语义召回，这是唯一有实质技术含量的可借鉴点
- 抽取/更新决策的 prompt 契约（ADD/UPDATE/DELETE/NOOP 显式动作词汇表）+ 自定义指令机制
- 反向教训：无质量门控的自动记忆抽取会自我放大（见 #4573），这条验证了 ACP 的确定性设计

**核心理由** — 增量（自动抽取 + 语义召回）对我不构成价值，因为我刻意要的是可读可回滚的记忆；而成本（每次 add 一次 LLM 调用 + 嵌入、一个向量库、热/冷上下文边界被自动注入打破、第三个记忆系统与 ACP 冲突）全部落在真实处。Star 数与 SOTA 宣称不进入判断：README 自认公开榜单分数来自托管平台"开源 SDK 不提供的专有优化"。

**主要风险** — (1) 若同时运行 ACP + auto-memory + mem0 = 三套记忆系统，正是我在 CLAUDE.md 5.5 已经解决过一次的冲突；(2) 开源版被官方定位为托管版的"teaser"，图记忆/整合/分析在 $249/月 Pro 之后，长期依赖的开源版可能停在引流定位；(3) Windows + 本地模型的坑密集（embedding 维度不匹配静默失败、api_key 未显式置 None 会静默回落 Pinecone 云、thinking 模型破坏 JSON 解析）。

**未验证事项** — `[未知]` 我刚读的是 README / issue / 定价页，**没有读 mem0 源码**，所以"新算法是否真在开源版里"、"DeepSeek 作为抽取模型的输出质量"都未验证。要验证需在隔离目录跑一次 30 分钟试验：本地 Ollama 或 DeepSeek + SQLite/Qdrant，喂 20 轮真实对话，然后**导出条目逐条人读**，统计有效率。此项只在触发条件成立时才值得做。

**下一步** — 无需行动。触发复查的条件：我要为**多用户**产品提供记忆（例如小蜘蛛对外服务），或我的记忆量增长到无法靠人读 md 维护。
